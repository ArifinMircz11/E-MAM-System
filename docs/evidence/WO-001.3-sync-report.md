## 2. Sync Queue Schema Standard

The standardized sync queue record schema structured in our `localDb.sync_queue` table:

```json
{
  "id": "SYNC_1720000000000_abc123",
  "tenantId": "madrasah01",
  "collection": "students",
  "action": "UPDATE",
  "payload": {
    "id": "STD001",
    "tenantId": "madrasah01",
    "namaLengkap": "Ahmad",
    "status": "Aktif",
    "updatedAt": "2026-07-02T10:00:00Z"
  },
  "status": "pending",
  "retryCount": 0,
  "lastAttempt": null,
  "createdAt": 1720000000000,
  "error": null
}
```

Standardized states during sync execution trace:
*   `PENDING`: Enqueued locally, awaiting trigger.
*   `PROCESSING`: Active execution lock engaged.
*   `SUCCESS`: Successfully applied to Cloud (`setDoc` / `deleteDoc`), removed from queue.
*   `FAILED`: Sync attempt encountered network latency or gateway error; scheduled for exponential backoff retry.
*   `CONFLICT`: Write conflict resolved via **Latest UpdatedAt Wins** strategy.

## 3. Pull & Push Synchronization Flow

### 3.1 Pull Delta Synchronization (Incremental Cursor Check)
1.  Read current cursor timestamp (`lastSyncAt`) from IndexedDB `syncMetadata` matching compound key `[tenantId+entity]`.
2.  If cursor exists, execute query on Firestore for documents matching `tenantId` where `updatedAt > lastSyncAt` (safety buffered).
3.  If no cursor exists, perform initial page partition fetch up to 500 documents.
4.  For each received document, compare with local IndexedDB record:
    *   If no local match: Write to Dexie immediately.
    *   If local match exists: Engage **Conflict Resolver**.
5.  Save the latest received `updatedAt` value back to `syncMetadata` as the updated cursor.

### 3.2 Push Synchronization (Self-Healing Queue Flush)
1.  Fetch all queue items with state `pending` or `failed`.
2.  Apply exponential backoff throttle (`Math.pow(2, retryCount) * 1000`) based on `lastAttempt` to prevent client resource crowding.
3.  For each item, convert payload schema via `EntityMapper` and validate with strict Zod types.
4.  Write to Firestore via isolated `dbGateway` (single Gateway boundary).
5.  Delete item from the queue upon successful completion.
6.  If item fails $\ge 5$ times or raises schema validation error, promote to `dead_letter_queue` for manual administrator repair.

---

## 4. Conflict Resolution Engine

Standard: **Latest UpdatedAt Wins**
*   **Case A**: Server entity `updatedAt` is greater than or equal to local entity `updatedAt`.
    *   *Result*: Server wins. Overwrite local record with the fresh server payload. Log event `CONFLICT_RESOLVED` to standard audit logs.
*   **Case B**: Local entity `updatedAt` is greater than server entity `updatedAt`.
    *   *Result*: Local wins. Retain local record and enqueue a standard mutation into `sync_queue` to overwrite the stale server version on the next sync push pass. Log event `CONFLICT_RESOLVED` to audit logs.
