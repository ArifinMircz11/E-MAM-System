PART 1: THE 10 CANONICAL QUESTIONS - SOURCE-CODE PROOF
--------------------------------------------------------------------------------

1. APA SUMBER CANONICAL IDENTITY SISWA?
   - JAWABAN: 'Student.idUnik' (contoh: 'STU-001' atau format 'STD-YYYY-[RANDOM]').
   - FILE: `/src/services/studentService.ts`
   - LINE: 125, 135-137
   - BUKTI:
     Sistem menghasilkan 'idUnik' sebagai basis identitas primer siswa saat 
     proses registrasi/pencatatan baru:
     ```ts
     const idUnik = data.idUnik || `STD-${new Date().getFullYear()}-${Math.random().toString(36).substring(2, 9).toUpperCase()}`;
     ```

2. APAKAH 'referenceId', 'id', ATAU 'idUnik' YANG MENJADI IDENTITY UTAMA?
   - JAWABAN: 'idUnik' adalah Canonical Identity utama dari siswa.
   - FILE: `/src/core/database/db.ts`
   - LINE: 369-376 (Dexie Schema Version 29/30)
   - BUKTI:
     Dexie operational database mendefinisikan 'idUnik' di urutan pertama (Primary Key) 
     pada skema tabel 'students':
     ```ts
     students: 'idUnik, id, tenantId, version, syncStatus, [tenantId+classId], ...'
     ```
     Untuk menjaga konsistensi, field 'id' dan 'studentsId' juga diisi secara 
     deterministik dengan nilai yang sama dengan 'idUnik' saat data baru dibuat:
     ```ts
     id: idUnik,
     studentsId: idUnik,
     ```

3. APA HUBUNGAN SecurityContext.referenceId DENGAN STUDENT?
   - JAWABAN: 'SecurityContext.referenceId' memetakan identitas pengguna aktif 
     (dari UserStore / AuthStore) ke 'Student.idUnik' yang bersangkutan.
   - FILE: `/src/core/security/contextHelper.ts` & `/src/hooks/useAuthInitialization.ts`
   - LINE: 85 (contextHelper.ts) & 157, 180 (useAuthInitialization.ts)
   - BUKTI:
     Saat inisialisasi sesi, 'referenceId' pengguna diatur dari 'studentId' 
     (yang menyimpan 'idUnik' siswa):
     ```ts
     referenceId: userData.assignment.studentId || userData.assignment.teacherId || null,
     ```
     Di layer service, 'SecurityContext.referenceId' digunakan untuk memvalidasi 
     bahwa siswa hanya dapat mengakses data miliknya sendiri (Least Privilege):
     ```ts
     if (secCtx.role === 'siswa' && secCtx.referenceId !== studentsId) { ... }
     ```

4. APA HUBUNGAN STUDENT IDENTITY DENGAN Attendance.studentId?
   - JAWABAN: 'Student.idUnik' dipetakan langsung ke 'Attendance.studentId' 
     dan 'Attendance.studentsId'.
   - FILE: `/src/features/attendance/services/attendanceService.ts`
   - LINE: 300, 331-332
   - BUKTI:
     Setiap record presensi yang dicatat via QR Scanner atau manual memetakan 
     'idUnik' siswa ke field 'studentId'/'studentsId' secara eksplisit:
     ```ts
     studentId: idUnik,
     studentsId: idUnik,
     ```

5. APAKAH Attendance MEMBUTUHKAN 'studentReferenceId'?
   - JAWABAN: TIDAK MEMBUTUHKAN.
   - FILE: All files in `/src/features/attendance/`
   - BUKTI:
     Penggunaan field redundan seperti 'studentReferenceId' dilarang keras untuk 
     mencegah polusi dan duplikasi skema data. Hasil audit membuktikan tidak 
     ada penggunaan kata kunci tersebut (PASS).

6. APAKAH ATTENDANCE referenceId MERUPAKAN IDENTITY RECORD ATAU IDENTITY SISWA?
   - JAWABAN: Format ID presensi bertindak sebagai IDENTITY RECORD (Primary Key 
     dari baris record presensi pada hari bersangkutan), sedangkan identitas 
     siswa tetap disimpan secara terisolasi di dalam field 'studentId' / 'studentsId'.

7. APAKAH `${studentId}_${date}` MERUPAKAN PRIMARY KEY ATTENDANCE ATAU referenceId?
   - JAWABAN: Merupakan PRIMARY KEY (id) dari entitas Attendance, baik secara 
     lokal di IndexedDB (Dexie) maupun dokumen di Cloud Firestore.
   - FILE: `/src/features/attendance/services/attendanceService.ts` & `/src/sync/handlers/attendance.handler.ts`
   - LINE: 287 (attendanceService.ts) & 11 (attendance.handler.ts)
   - BUKTI:
     ```ts
     // Di Service:
     const attId = `${idUnik}_${today}`;
     // Di Sync Handler:
     const attId = `${payload.studentId}_${payload.date}`;
     ```

8. APAKAH IDENTITY BERUBAH KETIKA: offline -> Dexie -> SyncQueue -> SyncEngine -> Firestore?
   - JAWABAN: TIDAK BERUBAH (Deterministik dan Stabil).
   - ALUR:
     1. Offline (QR Scan): Kode QR membawa 'idUnik' -> lookup di 'Dexie.students' via 'idUnik' -> Siswa ditemukan secara instan.
     2. Dexie: Record presensi dibuat dengan ID unik `${idUnik}_${date}`.
     3. SyncQueue: Payload dikirimkan dengan key 'studentId' & 'id' yang sama tanpa modifikasi.
     4. SyncEngine / Firestore: Handlers memetakan payload langsung ke dokumen Firestore menggunakan path `attendance/${payload.studentId}_${payload.date}` tanpa random document generator (idempotent & deterministic).

9. APAKAH TERDAPAT FALLBACK IDENTITY CHAIN YANG AMBIGU?
   - JAWABAN: TIDAK. 
   - PENJELASAN: Seluruh fallback diarahkan secara terstruktur ke `idUnik || id || studentsId`. Karena pada saat registrasi awal `id = idUnik = studentsId`, nilai-nilai ini dijamin 100% konsisten dan tidak ambigu.

10. APAKAH ADA DATA MIGRATION YANG BERPOTENSI MENGUBAH IDENTITY?
    - JAWABAN: TIDAK ADA.
    - PENJELASAN: Skema Dexie versi 29/30 telah menetapkan 'idUnik' sebagai primary key yang paten untuk tabel 'students', sehingga tidak ada migrasi skema yang berpotensi memutasi atau mencederai data identitas yang sudah ada.

  -> STATUS: VERIFIED / COMPLIANT.
